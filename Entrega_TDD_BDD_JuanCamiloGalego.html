Descripción de la actividad

Práctica individual para derivar casos de prueba a partir de un escenario y aplicar dos enfoques en código: TDD, mediante el ciclo rojo–verde–refactor, y BDD, mediante un escenario Dado–Cuando–Entonces en Gherkin. Este trabajo practica el flujo requerido para avanzar en E2.1.

La actividad reúne el Excel con los casos derivados, el código y la evidencia del ciclo TDD, y un escenario BDD conectado a código real. La entrega se hace mediante el enlace al repositorio personal del estudiante.

Fecha indicada en la guía: jueves 29 de octubre de 2026, 11:59 p. m. La elaboración de este trabajo corresponde al 31 de octubre de 2026; la fecha de la guía se conserva.

Instrucciones de la actividad

Los siguientes pasos resumen los requisitos de la guía. El desarrollo presentado después aplica estos requisitos al escenario C.

1. Derivar y registrar los casos de prueba

  1. Elegir uno de los escenarios propuestos: exportación de reportes, suavización con tendencia (Holt) o bloqueo de cuenta. También se puede usar una situación del módulo propio del proyecto, informándola al docente. No repetir el escenario trabajado en clase ni el del examen.
  2. Completar la hoja Casos de la plantilla suministrada con mínimo 6 casos: ID, qué se prueba, categoría, entrada y resultado esperado.
  3. Cubrir al menos una vez las cuatro categorías: Válido, Inválido, Límite y Permisos. Usar la lista desplegable de Categoría y dejar vacías las filas que no se utilicen.
  4. Renombrar el Excel con el nombre del estudiante: Casos_de_Prueba_NombreApellido.xlsx.

2. Implementar un caso con TDD

  1. Rojo: escribir primero una prueba para un cálculo o una regla de validación, ejecutar y guardar la salida que muestra el fallo.
  2. Verde: implementar el código mínimo que permite pasar la prueba y guardar la salida de ejecución.
  3. Refactor: mejorar el código sin cambiar su comportamiento, ejecutar de nuevo y guardar la evidencia de que sigue pasando.

Si el resultado es numérico, comprobarlo con tolerancia; por ejemplo, con toBeCloseTo en Jest. El caso elegido debe poder ejecutarse sin una interfaz gráfica. Se recomiendan tres commits separados para evidenciar el ciclo.

3. Implementar otro caso con BDD

Elegir otro caso, distinto del usado en TDD, y escribir un archivo .feature en español con al menos un escenario Dado–Cuando–Entonces. Implementar los pasos que lo conectan con código real y ejecutar la prueba.

El archivo Gherkin debe comenzar exactamente con # language: es en su primera línea, sin una línea vacía ni un comentario antes.

4. Publicar y entregar

Subir los archivos al repositorio personal, con el Excel en docs/pruebas/actividades/semana4/, las pruebas unitarias en tests/unit/ y el escenario y los pasos BDD en tests/bdd/. Entregar al docente el enlace que permite revisar el trabajo. La guía no exige un pull request.

Desarrollo de la actividad

Escenario elegido: C. Una cuenta se bloquea temporalmente después de cinco intentos fallidos de inicio de sesión consecutivos. El bloqueo dura quince minutos.

Relación entre los casos y la implementación
ParteAplicación al escenarioEvidencia
Casos derivados12 casos, CP-01 a CP-12, que cubren las cuatro categorías.Plantilla de Excel diligenciada y renombrada con el nombre del estudiante.
TDD · CP-08Calcular los minutos restantes del bloqueo: después de 30 segundos deben quedar 14,5 minutos.Prueba unitaria con tolerancia numérica; salidas de rojo, verde y refactor.
BDD · CP-05Denegar el acceso con contraseña correcta mientras el bloqueo continúa vigente.Escenario en español y pasos que ejecutan la regla de acceso.

Supuestos adoptados

  • El quinto fallo inicia el bloqueo. Su vigencia incluye el instante de inicio y termina exactamente quince minutos después.
  • Un acceso correcto antes del quinto fallo reinicia el contador de fallos consecutivos.
  • Un intento durante el bloqueo no extiende el plazo, aunque la contraseña sea correcta.
  • El estado de cada cuenta es independiente. Las pruebas usan tiempos controlados para comprobar los límites sin esperar quince minutos reales.

Estas decisiones hacen explícitos los detalles que el enunciado no desarrolla. No se introduce un permiso de administrador para saltarse el bloqueo.

Cómo ejecutar las pruebas

Se utiliza JavaScript con Node.js, Jest y jest-cucumber. Con Git y Node.js 22 o posterior instalados, abrir una terminal y ejecutar:

git clone --branch actividad-tdd-bdd-semana4 https://github.com/Kamilogallego/Kamilogallego.git
cd Kamilogallego
npm ci
npm test

Para revisar cada grupo por separado:

npm run test:unit
npm run test:bdd

Los comandos de descarga requieren que esté publicada la rama actividad-tdd-bdd-semana4. Si ya se dispone de la carpeta de la actividad, abrir una terminal en ella y ejecutar npm ci y npm test.
